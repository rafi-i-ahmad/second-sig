## Which pass is wrong where

### Backward pass: no errors on 13 cases

Every movement, allowance and config change the trace shows was listed, with the right amount in
base units, the right parties by address, and citations that all resolve (zero uncited claims
across 13 narrations, 41 effects). Specific things it got right that were not guaranteed:

- Aave: three movements as two structured items plus a sentence (USDC out, aUSDC mint in), and
  Aave's seven opaque reserve-accounting slot writes summarised as one `info` effect.
- Uniswap (case 10): USDC to the pair, WETH legs, ETH back to the Safe "from Uniswap router",
  amounts exact to the wei; the pair -> router WETH leg correctly not listed as a Safe movement.
- Bybit: the delegatecall and the singleton overwrite both `critical`, nothing else elevated.
- Mint/burn parties given as the zero address, never as a token symbol.

One thing to keep an eye on: severity is applied as the prompt says, which makes an **owner or
threshold change `critical`** (case 04). With the decision table as written, an owner change the
words do not mention is therefore REJECT, not ASK. That is the right outcome for case 35 and
probably for real life, but it is a choice: if we want ASK there, the prompt's critical tier
should drop "owners" and keep singleton/guard/fallback/modules.

### Forward pass: one real gap

**Aave (demo).** The recorded forward form reads "Deposit 10,000 USDC into Aave v3" as USDC out
plus the implied approval, and does **not** list the aUSDC receipt token coming back. The earlier
hand-written intent and the Argon dry run of 22 October both did. Flash at thinking low is
inconsistent here. Two ways to close it, pick one:

1. *Prompt (proposed, not applied).* In `forward.py` SYSTEM, after "A deposit into a protocol
   implies an approval to that protocol for the same amount", add: "A deposit into a lending
   protocol also returns a receipt token (Aave: aTOKEN, Compound: cTOKEN) to the depositor; list it
   as a movement in, amount as deposited if the protocol mints 1:1, otherwise None."
2. *Tolerance (applied).* `inbound_from_callee`: an asset the Safe *receives* from inside its call
   into a contract the words license is explained. Receiving cannot drain the Safe, and the
   outbound leg still has to match on its own. This is what makes Aave MATCH today.

Both are reasonable; (2) is the safer default because it does not depend on the model knowing
every protocol's receipt token, and the match is flagged in every report where it fires.

**Not errors, by design.** 09, auditor and Bybit show "forward vs truth" differences because the
*words* do not say what the bytes do. The forward pass is correct to follow the words; the
comparison is what turns the gap into ASK or REJECT. The report labels these `real_finding`.

### The open design question: contradiction vs omission

Today's table says: an observed effect nothing expected explains is ASK if `notable`, REJECT if
`critical`. That makes the auditor case (true but incomplete) ASK, which scenario 3 wants, and it
also makes 31–34 ASK, which the fixtures say should be REJECT.

The difference between them is not severity, it is *kind*: the auditor description is incomplete;
the 31–34 descriptions are **wrong**. In each of 31–34 the comparison sees both halves at once:
an expected item the trace does not show *and* an observed item of the same kind and asset that
nothing explains. That pair is a contradiction, and no honest proposer produces one.

Proposed rule (not applied; one function in `verdict.py`, one test per case):

> If `expected_unobserved` and `observed_unexplained` contain items of the same kind for the same
> asset, the description contradicts the bytes → **REJECT**. An unexplained observed item with no
> expected counterpart (omission) stays ASK. An expected item with no observed counterpart (the
> words promise more than happens) stays ASK.

On the recorded forms this gives 31, 32, 33 and 34 → REJECT, keeps auditor → ASK, 09 → ASK, and
leaves every MATCH untouched. It needs a decision because it changes a verdict row, not a tolerance.

The alternatives considered: making an unmentioned unlimited approval `critical` (catches 31 only,
and flips the auditor demo to REJECT), or the floor rule "approve to an EOA" (catches 31 and 33,
nothing else). Neither covers 32 or 34; the contradiction rule covers all four.
